# Intent-Based Instructions for Coding Agent

## Context

The `mpp_explorer` package has been refactored from a monolith into modules. The 3D visualisation feature is currently broken: the exported HTML uses ES module `import` statements pointing at a CDN, which fails on two counts — (a) the nested bare specifier `'three'` inside OrbitControls can't resolve without an import map, and (b) modern browsers block ES modules when the page is opened from `file://`, because `file:` URLs are treated as opaque origins.

A previous iteration of the codebase supported two working modes — a dynamic mode (local HTTP server on `127.0.0.1`) and a static mode (standalone HTML). Both were lost in the refactor. Restore both, and make both work offline.

---

## Goal

Restore two clearly separated 3D visualisation modes with an offline-capable, CDN-free delivery mechanism.

- **Static mode** — export a single self-contained HTML file that works when double-clicked from disk (`file://`), with no network access, no server, and no CDN.
- **Dynamic mode** — write the viewer into the reports directory and serve it from a short-lived local HTTP server on `127.0.0.1`, opening it in the default browser.

Both modes share the same inlined Three.js and OrbitControls assets. Neither mode may reference any external URL at runtime.

---

## Constraints and non-goals

- Do **not** reintroduce CDN URLs or ES module `import` statements. The exporter output must not contain the strings `unpkg.com`, `cdn.jsdelivr.net`, `import * as THREE`, or `type="module"`.
- Do **not** change any other reporting behaviour (CSV export, graph payload shape, analysis layer).
- Do **not** add new third-party Python dependencies. The local server must use only `http.server`, `socketserver`, `socket`, `threading`, and `functools` from the standard library.
- Do **not** modify `app.py` beyond the two handlers named below and the top-of-file import block.
- Preserve the existing public API surface of the `reporting` package where possible; new names are additions, not replacements that break callers, **except** for the two removed functions noted in step 4.

---

## Work items

### 1. Add vendored JavaScript assets

Create a new directory `mpp_explorer/reporting/assets/` containing two files:

- `three.min.js` — the UMD build of Three.js **release r147** (this is the last release that ships a classic-global UMD build; later releases are modules-only). Source: `https://unpkg.com/three@0.147.0/build/three.min.js`.
- `OrbitControls.js` — the non-module script variant of OrbitControls for the same release. Source: `https://unpkg.com/three@0.147.0/examples/js/controls/OrbitControls.js`. This file attaches `THREE.OrbitControls` to the global `THREE` object; it must not contain an `import` statement.

Download both files once and commit them into the repository. They must travel with the package. Do not fetch them at runtime.

Update package data configuration so that `mpp_explorer/reporting/assets/*.js` is included when the package is installed or distributed. For a setuptools-based `pyproject.toml`, add a `[tool.setuptools.package-data]` entry mapping `"mpp_explorer.reporting"` to `["assets/*.js"]`. If the project uses a different build backend, use its equivalent mechanism.

### 2. Create `mpp_explorer/reporting/html_builder.py`

Introduce a new module responsible for composing the viewer HTML.

**Public API:** a single function `build_viewer_html(payload: dict) -> str`, where `payload` is the output of `analysis.build_overlay_graph`. Returns the complete HTML document as a string.

**Behaviour:**

- Load `three.min.js` and `OrbitControls.js` from the sibling `assets/` directory. Cache the file reads with `functools.lru_cache`. If either file is missing, raise `FileNotFoundError` with a message naming the missing path and stating that both files are expected beside this module.
- Embed the two JavaScript sources **inline** in `<script>` tags — not `<script src="...">`, not `type="module"`.
- Serialise `payload` to JSON and inject it as a JavaScript object literal assigned to a `GRAPH` constant.
- The resulting document must contain the viewer code currently living inside `threejs_export._build_html`, adjusted as follows:
  - Remove the two `import` statements at the top of the module script.
  - Remove the `type="module"` attribute from the script tag.
  - Change `new OrbitControls(...)` to `new THREE.OrbitControls(...)`.
  - Change `renderer.outputColorSpace = THREE.SRGBColorSpace` to `renderer.outputEncoding = THREE.sRGBEncoding`. This is the r147 API; `outputColorSpace` does not exist in that release.
- Preserve every other behaviour of the existing viewer exactly: scene setup, fog, camera, orbit controls, lighting, starfield, node and edge construction, the spring simulation, raycaster-based picking, tooltip, HUD search, edge-visibility toggles, the "Stabilise" button, `stabiliseLayout(260)` on startup, and the `animate()` loop.

Keep the HTML template in this module as a module-level string constant, formatted with the three inputs (Three.js source, OrbitControls source, graph JSON). Use doubled braces inside the template so Python's `str.format` leaves the JavaScript's braces untouched.

### 3. Rewrite `mpp_explorer/reporting/threejs_export.py`

Replace the current single-function implementation with the two exported functions described below. Retain the module's existing import of `build_overlay_graph` from `..analysis` and its import of `Project` from `..model.project`.

**`export_static_viewer(project: Project, output_html: str | Path) -> Path`**

- Build the overlay graph payload from `project`.
- Compose the HTML via `build_viewer_html`.
- Ensure the parent directory of `output_html` exists (`Path.mkdir(parents=True, exist_ok=True)`).
- Write the HTML with UTF-8 encoding.
- Return the resolved `Path`.

This function must not start a server and must not open a browser.

**`open_dynamic_viewer(project: Project, reports_dir: Path, filename: str = "_preview_3d.html") -> str`**

- Build the overlay graph payload.
- Ensure `reports_dir` exists and write the HTML to `reports_dir / filename`.
- Choose a free TCP port on `127.0.0.1` using a socket bound to port 0, reading `getsockname()[1]`, then closing the socket. Cache this value with `functools.lru_cache(maxsize=1)` so a session reuses one port across preview invocations.
- Start a `socketserver.TCPServer` bound to `("127.0.0.1", port)` with a `SimpleHTTPRequestHandler` subclass, using `functools.partial` to pass `directory=str(reports_dir)` to the handler constructor.
- Silence per-request logging by overriding `log_message` on the handler subclass to do nothing. This matters because the default handler prints to stderr on every asset fetch.
- Set `httpd.daemon_threads = True` and run `httpd.serve_forever()` on a `threading.Thread` marked as a daemon. The thread must not block shutdown of the Python process.
- Open `http://127.0.0.1:{port}/{filename}` in the default browser via `webbrowser.open`.
- Return the URL string.

Rationale for caching the port: repeated previews within a session should rewrite the same file at the same URL, giving the user a stable address and reusing one server thread rather than spawning a new server each time. If the agent prefers a fresh port per call, that is acceptable, but document the choice in a module-level comment.

### 4. Update `mpp_explorer/reporting/__init__.py`

- Remove the import and re-export of `export_threejs_visualization`. That name no longer exists.
- Import and re-export `export_static_viewer` and `open_dynamic_viewer` from `.threejs_export` in its place.
- Keep the existing re-export of `export_tree_to_csv` unchanged.
- Update `__all__` to match. The final contents should be `export_tree_to_csv`, `export_static_viewer`, and `open_dynamic_viewer`.

### 5. Update `mpp_explorer/app.py`

Two changes only.

**Import block.** Replace the current `from .reporting import export_threejs_visualization, export_tree_to_csv` line with an import of `export_static_viewer`, `export_tree_to_csv`, and `open_dynamic_viewer`. Do not remove or reorder any other import.

**Method bodies.** Replace `open_3d_preview` and `export_3d_visualisation` with versions that use the new API.

`open_3d_preview` should:

- Warn and return if no project is loaded (existing behaviour).
- Derive a source name from `self.current_file.stem` or fall back to `"programme"`.
- Call `open_dynamic_viewer(self.project, self.reports_dir(), filename=f"{source_name}_3d_preview.html")`.
- On success, set `self.status_text` to a message including the returned URL.
- On exception, show an error dialog via `messagebox.showerror("3D preview failed", str(exception))`.

`export_3d_visualisation` should:

- Warn and return if no project is loaded.
- Derive the source name the same way.
- Prompt for a save path via `filedialog.asksaveasfilename`, defaulting to the reports directory, with initial filename `f"{source_name}_3d_visualisation.html"`, default extension `.html`, and filetypes for HTML and all files.
- Return silently if the user cancels.
- Call `export_static_viewer(self.project, filename)`.
- On success, set the status text to include the output path, then ask via `messagebox.askyesno` whether to open the file. If yes, open it with `webbrowser.open(output.resolve().as_uri())`. Note that this is `file://` and it will now work, because the exported HTML no longer loads any external resource.
- On exception, show `messagebox.showerror("Visualisation export failed", str(exception))`.

No other methods, menus, or toolbar entries need to change. The existing menu and toolbar entries that call these two methods continue to work.

### 6. Delete dead code

The old `_build_html` function and the old `export_threejs_visualization` function must not remain anywhere in the package. Search the tree for both names and remove any remaining references, docstrings, or comments that mention them.

## Verification checklist

After the changes, a coding agent or reviewer should be able to confirm all of the following by inspection or by running the application.

1. `python -c "from mpp_explorer.reporting import export_static_viewer, open_dynamic_viewer, export_tree_to_csv"` succeeds.
2. `grep -R "unpkg.com\|cdn.jsdelivr.net\|type=\"module\"" mpp_explorer/reporting/` returns no matches inside the Python sources.
3. Opening the MPP file and choosing **File → Export 3D visualisation...** writes an HTML file. Double-clicking that file in the OS file manager opens it in a browser with the 3D graph visible. No console errors about module specifiers or `file:` origins appear.
4. Opening the MPP file and choosing **File → Open 3D preview** (or the toolbar equivalent) opens a browser to `http://127.0.0.1:<port>/<name>_3d_preview.html` with the same graph visible. The terminal running the Python app shows no per-request log lines.
5. Closing the Python application releases the port and terminates the server thread without a hang. Verify by rerunning the app immediately and confirming the preview loads.
6. The exported HTML file works with the machine's network adapter disabled.
7. CSV exports via the File menu continue to behave as before.

## Risks and notes for the agent

- **Three.js version pin.** r147 is not the latest release. It is deliberately chosen because it is the last release with a UMD build. Do not "upgrade" it, because that would force a return to ES modules and reintroduce the `file://` problem. If a future feature requires a newer Three.js, the correct response is a bundler step that produces a single inline UMD artefact, not a direct CDN import.
- **OrbitControls API drift.** Between r147 and current releases, the class constructor and the `enableDamping`/`dampingFactor` properties are unchanged, but other methods have been added and a few renamed. Keep to the subset already used by the viewer code.
- **Renderer colour handling.** r147 uses `renderer.outputEncoding = THREE.sRGBEncoding`. Setting `renderer.outputColorSpace` on r147 is a silent no-op that leaves the renderer in linear space, which produces visibly dark output. This is why the change is called out explicitly in step 2.
- **Port caching.** Because `_free_port` is cached, the server is bound once per Python process. If a caller invokes `open_dynamic_viewer` twice, the second call rewrites the HTML file at the same URL and reopens the browser. This is intentional. If the agent chooses not to cache, note that the first server thread remains running until process exit, which is harmless but accumulates threads over many invocations.
- **Asset size.** `three.min.js` is on the order of 600 KB. Inlining it into every exported report produces files of similar size. This is acceptable for the stated use case (portable, offline, single-file reports). If report size later becomes a concern, the correct fix is an external `.js` sidecar shipped alongside the HTML, not a CDN reference, because CDN references reintroduce the offline and origin problems.
